## 🎯 重要な意思決定

### 通知設計を CALENDAR repeats:true に統一

**選択肢**:
- A. 毎日新たに DATE トリガーで 1日分をスケジュール（起動依存）
- B. CALENDAR + repeats:true で固定識別子の繰り返し通知 ← **採用**
- C. Background Task（BGTaskScheduler）で複雑な分岐処理

**採用理由**:
- アプリが起動されなくても確実に発火
- iOS の通知スロット（64個まで）を圧迫しない（4個固定）
- 識別子ベースの再スケジュールで「設定変更時の差し替え」が単純

**トレードオフ**（受け入れ）:
- バックグラウンド時は「服薬済み」記録後も当日の追加リマインダーが鳴ってしまう
  - フォアグラウンドハンドラで抑制するのみ可能
  - 仕様書「3段階リマインダー」と整合するので Phase 1 では許容

### buildNumber 管理を EAS リモート + autoIncrement に変更

- Apple 側にすでに Build 1 がある、Day 5 で Build 2 を作った形跡もあり、衝突回避のため大きめの番号（10）から再スタート
- `appVersionSource: "remote"` で今後は EAS サーバー側が管理

## 📝 技術的なメモ

### 1. expo-notifications のトリガー種別

| トリガー | 繰り返し | 用途 |
|---------|---------|------|
| `DATE` | 不可（1回限り） | スヌーズ等の単発 |
| `CALENDAR` | `repeats: true` で可能 | **毎日の固定時刻リマインダー** |
| `TIME_INTERVAL` | `repeats: true` で可能 | N秒ごとの繰り返し |
| `DAILY` | 自動的に毎日 | iOS/Android 両対応の簡易版 |

→ 今回は CALENDAR を採用（hour/minute 指定 + repeats）

### 2. CALENDAR repeats:true の制約

- `data.doseRecordId` を事前に決められない（毎日違う dose record に紐づく必要があるため）
- → **ハンドラ側で動的解決**:
  ```typescript
  async function resolveTodaysDoseRecordId() {
    const medication = await getActiveMedication();
    const sheet = await getCurrentSheet(medication.id);
    return (await getTodaysDoseRecord(sheet.id))?.id ?? null;
  }
  ```

### 3. EAS buildNumber 自動化

- `eas.json` の `cli.appVersionSource: "remote"` → EAS サーバー側でバージョン管理
- `eas.json` の build プロファイルに `autoIncrement: true` → 毎回 +1
- `eas build:version:set --platform ios` でリモート値を明示設定可能
- `eas build:version:get --platform ios` で現在値を確認可能

### 4. App Store Connect の buildNumber ルール

- 同じ version（例: 1.0.0）内で buildNumber は **必ず単調増加**
- 一度使った番号は再利用不可（削除しても）
- → 衝突したら **大きめの番号にジャンプ** するのが最も簡単

## 💡 学んだこと・注意点

### 1. iOS の通知スケジューリングは「予約モデル」

`expo-notifications` の `scheduleNotificationAsync` は **iOS の UNUserNotificationCenter に予約を入れる** だけで、アプリが起動していなくても OS が発火させる。

→ つまり「DATE で 1 個だけ予約」だと、その 1 回が終わったら **永遠に何も鳴らない**。

これが今回のバグの本質。「翌日になったら自動で再スケジュールされる」と暗黙に期待していたが、そんな仕組みは expo にも iOS にもない。

### 2. TestFlight 実機テストの価値

シミュレータでは:
- 通知の発火タイミングを正確に再現できない（時計の概念がアプリ起動中のみ）
- バックグラウンド・未起動時の挙動が見えない

→ **Phase 1 のコア機能は必ず TestFlight 実機で 24 時間以上の連続検証** が必要。今回も実機テストで初めて発見できた。

### 3. EAS buildNumber は最初から設定すべき

新規プロジェクトを始める際は **最初の段階で**:
- `eas.json` に `"autoIncrement": true` を入れる
- `appVersionSource: "remote"` で EAS 側管理

これをやっておけば、Day 5 で「Build 2 のつもりが Build 1 だった」事故を防げた。

### 4. 仕様書を読み返す習慣

今回のバグは、仕様書 `01_pilllog.md` 5.x に明記されている22時通知が **実装段階で見落とされていた**。

→ **Phase 完了の判断基準を「仕様書の各章をチェックリスト化」する** べき。
